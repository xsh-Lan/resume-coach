# 简历改写工作流

## Phase 1：读取事实

1. 读取用户原始简历、项目材料和目标 JD。
2. 建立“事实表”：教育、经历、项目、技能、结果、个人贡献。
3. 标记：已验证、待确认、不可证明、预计/目标。

未建立事实表前不得改写。

## Phase 2：解析 JD

把 JD 拆成：

- 业务场景
- 核心能力
- 工具/技术
- 结果责任
- 协作复杂度

把要求标记为必须项、加分项、弱相关、无法证明。

## Phase 3：选择案例模式

从 `case_patterns.md` 选择最多三个：

1. 背景转换最接近。
2. 目标岗位证据最接近。
3. 量化或项目深度最强。

案例只用于结构，不复制事实。

## Phase 4：建立证据矩阵

| JD 要求 | 用户证据 | 证据强度 | 可量化指标 | 缺口 |
|---|---|---|---|---|

优先使用：

1. 有基线和结果的业务指标。
2. 有交付范围和数量的项目。
3. 有上下游影响的效率/质量结果。
4. 能说明复杂度和个人贡献的事实。

## Phase 5：改写

每段经历：

1. 一行摘要。
2. 2-4 条 bullet。
3. bullet 使用“问题—动作—结果”。
4. 技术方法与业务价值绑定。
5. 预计结果写“预计/目标”。

## Phase 6：岗位重排

- AI 产品：技术路径 → 闭环 → 评测/人审 → 业务结果
- 数据产品：指标治理 → 平台 → 用户迁移 → 成本效率
- 商业分析：问题 → 数据/模型 → 策略 → 经营结果
- 增长运营：分层 → 机制 → 转化/ROI → SOP
- B 端产品：SDK/API/控制台 → 客户交付 → 客户价值 → 商业化
- 供应链：计划 → 交付 → 质量 → 库存 → 成本

## Phase 7：三道校验

### 事实校验

每个数字、职位、日期、上线状态都能回到原始材料。

### 匹配校验

第一屏是否明确目标岗位、核心能力和结果。

### 诚信校验

没有夸大个人贡献，没有把团队成果写成个人成果，没有把计划写成已完成。

## Phase 8：输出

- 修改后的简历
- 逐条修改说明
- 仍需用户补充的事实/数字
- 岗位匹配风险和面试追问点
